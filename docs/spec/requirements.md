# DDG Agents 제품 요구사항

이 문서는 지금까지 합의한 제품 동작을 정리한다. 초기 범위와 미결정 사항은 마지막에 따로 둔다.

## 1. 제품과 경계

- **DDG Agents**는 Rust 코어를 사용하는 멀티플랫폼 데스크톱 앱과 운영자 CLI(`ddg`)로 구성된다. 사람은 GUI에서 봇·팀·스페이스·세션을 주 관리·검토하며, `ddg` CLI는 세션·에이전트 실행 및 자동화·운영자 인터페이스 역할을 담당한다.
- GUI를 먼저 만들고 화면을 직접 확인하면서 기능을 점진적으로 붙인다. GUI 창의 수명과 작업 실행은 분리해, 창을 닫았다 열어도 진행 중인 작업을 다시 확인할 수 있게 한다.
- 기존 `dotdotgod` CLI는 프로젝트 콘텍스트·문서·문서 그래프를 관리하는 별도 도구다. DDG Agents는 그 기능을 재구현하지 않으며, 필요한 봇에는 기존 CLI를 툴로 배정할 수 있다.
- **제품 목표:** 입력, 작업 범위, 완료 기준과 인계를 구체화해 봇이 깊은 추론에 크게 의존하지 않고도 일을 수행하게 한다. DDG 제품 자체에 특정 모델이나 `thinking: low`를 하드코딩 기본값으로 지정하지 않으며, 사용자 설정(`~/.config/ddg/agents.json`)으로만 기본 에이전트와 실행기 프리셋을 구성한다.

## 2. 실행 위치와 세션

| 개념 | 정의 |
|---|---|
| 머신 (`Machine`) | 봇이 실행되는 로컬 또는 원격 호스트 |
| 스페이스 (`Space`) | 특정 머신의 절대 디렉토리 경로. 경로 문자열이 같아도 머신이 다르면 별도 스페이스 |
| 세션 (`Session`) | 특정 봇을 특정 스페이스에서 실행한 인스턴스. 각 세션은 고유 ID와 실행 상태·결과를 가진다 |
| 팀 실행 | 특정 스페이스에서 팀 워크플로우를 한 번 실행한 기록. 봇 세션과 구분한다 |

실행 머신과 시작 작업 디렉토리(`cwd`)는 스페이스에서 결정한다. 경로는 대상 머신에서 확인하며, 접근할 수 없으면 실행을 실패 처리한다. `cwd`는 파일 접근을 제한하는 보안 경계가 아니다. 머신 연결 단절만으로 세션 종료를 단정하지 않는다.

세션은 부모 세션을 참조할 수 있다. 부모는 자식에 작업 지시와 필요한 맥락을 전달할 수 있지만, 툴 권한이나 시크릿은 상속하지 않는다. **부모·자식은 누가 실행을 요청했는지, 워크플로우 연결은 결과를 어디로 넘기는지**를 나타낸다. 팀 호출만으로 가짜 봇 세션을 만들지 않는다.

## 3. 봇, 스킬, 툴

- 봇은 팀과 독립적으로 존재하며, **자기 에이전트 마크다운, 스킬 구성, 입출력 계약**을 가진다. 마크다운에는 역할·원칙·제한을, 스킬에는 작업 절차와 예시를 둔다. 봇 계약은 단독 실행과 팀 내 실행에 공통으로 적용된다.
- DDG Agents는 스킬과 MCP·CLI 같은 툴을 중앙에서 등록하고, 봇별 스킬 버전과 툴 권한을 배정한다. 각 세션과 호출된 팀의 봇은 자신의 배정으로 실행한다. 스킬 수정으로 툴 권한을 늘릴 수 없다.
- 같은 봇의 여러 세션은 동시에 스킬 개선안을 제출할 수 있다. 제안에 기준 버전, 변경 내용, 근거 세션을 남기고, 현재 버전과 비교하여 기존 변경을 덮어쓰지 않게 한다. 승인된 버전은 해당 봇의 다음 세션부터 적용되며, 진행 중인 세션과 다른 봇의 배정은 변경하지 않는다.
- 팀 또는 스페이스에만 적용되는 지침은 해당 범위에 둔다. 봇의 공통 스킬을 불필요하게 바꾸지 않는다.

## 4. 에이전트 실행기, 터미널 통신과 실행 조건

- 봇의 실제 작업은 **Pi, Claude Code, Codex 같은 기존 에이전트 실행기**에 맡긴다. 봇은 사용할 실행기를 지정하며, DDG Agents는 스페이스가 가리키는 머신에서 해당 실행기를 호출한다. 자체 에이전트 엔진을 만들지 않는다.
- 봇의 역할·스킬·입출력 계약은 실행기와 구분한다. DDG Agents는 선택한 실행기에 봇의 작업 지시와 설정을 전달하고, 실행기의 결과를 공통 작업 응답으로 받아 세션과 팀 워크플로우를 관리한다.
- 봇 간 통신은 터미널 인터페이스를 기반으로 한다. 사람에게 보여주는 로그와 기계가 읽는 메시지를 구분한다. 자연어 로그만으로 완료를 판단하지 않는다.
- 작업 요청에는 작업 ID, 지시, 입력 자료, 완료 기준을 담는다. 응답에는 같은 작업 ID, 상태, 구조화된 결과와 필요한 산출물 참조를 담는다. DDG Agents가 결과를 검증하고 팀 규칙에 따라 인계한다.
- **봇과 팀 모두** 수동 실행, 특정 트리거에 의한 실행, 상시 운영 대상이 될 수 있다. 실행 조건은 대상과 스페이스에 연결한다. 상시 운영은 요청을 계속 받을 수 있다는 뜻이며, 개별 팀 실행은 여전히 시작과 끝이 있다.

## 5. 팀과 워크플로우

- 팀은 **봇 그룹과 그 협업 워크플로우를 합친 정의**다. 한 봇은 여러 팀에 속할 수 있고, 같은 구성원이라도 워크플로우가 다르면 별도 팀을 만들 수 있다.
- 작업 노드는 **봇 노드**와 **팀 노드**뿐이다. 봇 노드는 봇 세션을 실행하고, 팀 노드는 다른 팀을 호출해 그 팀의 종료 결과를 받는다. 호출자는 상대 팀의 내부 구성이 아니라 입출력 계약을 사용한다.
- 각 단계는 담당 봇 또는 팀, 입력, 작업 범위, 완료·판정 기준, 출력, 결과별 인계를 정의한다. 인계 대상은 봇 이름이 아니라 **워크플로우 단계 또는 종료점**이다. 같은 봇이 한 팀에서 여러 역할을 맡을 수 있다.
- 워크플로우는 **시작점 하나**에서 출발하고 모든 분기는 명시된 종료점에 도달해야 한다. 종료점은 여러 개일 수 있다. 명시적 루프 외의 되돌아가는 연결과 `A → B → A` 같은 팀 호출 재귀는 허용하지 않는다. 같은 팀을 루프 안에서 반복 호출할 수는 있다.
- 루프는 별도 노드 유형이 아니라 실행 규칙이다. 반복 구간, 통과 조건, 첫 회차를 포함한 최대 횟수, 통과 경로, 한도 도달 처리 경로를 명시한다. 한도 도달 경로는 다른 팀을 거치는 경우에도 해당 루프에 재진입할 수 없다.
- 예: `수정 팀 → 평가 봇`을 최대 10회 실행한다. 80점 이상이면 즉시 통과한다(10회차도 포함). 80점 미만이면 1~9회차에서만 다시 수정하고, 10회차에는 미리 정한 미통과 처리로 이동한다. 실행 실패나 잘못된 출력은 기준 미달과 구분한다. **평가는 봇이 하고, 결과 검증·분기·인계·반복 횟수 관리는 Rust 코어가 한다.**

## 6. 임시 봇과 임시 팀

- 임시 봇과 임시 팀은 별도 형식이 아니라 **한 번 실행하고 보관하는 봇·팀 정의**다. 임시 봇은 자식 세션 하나에 배정한다. 임시 팀은 기존 봇·팀을 조합하거나 임시 봇을 포함할 수 있다.
- 사용자는 GUI에서 임시 팀을 구성하고, 봇은 내부 인터페이스로 임시 봇 또는 임시 팀을 요청할 수 있다. 구성과 실행 권한은 별개이며, 임시 구성으로 호출 권한이나 툴 권한을 우회할 수 없다.
- 성공·실패·취소 후 일반 목록과 실행 대상에서는 제외하되, 사용한 정의, 작업·단계 결과, 요청 출처, 스킬 버전과 툴 배정은 분석용으로 남긴다. 시크릿 값은 기록하지 않는다.
- 보관 기록을 비교해 반복적으로 필요한 역할이나 협업 방식을 찾고, **새 영구 봇이나 팀의 초안**으로 만들 수 있다. 보관된 정의를 다시 활성화하거나 자동 등록하지 않는다. 영구 팀에 임시 봇 참조가 있다면 검토 후 영구 봇으로 등록하거나 교체한다.

## 7. 운영자·에이전트 CLI와 업데이트

- `ddg`는 머신·룸·세션 관리, 에이전트 프로필 및 실행, 세션 간 메시징을 제공한다. 관리 PTY 안의 메시징은 주입된 인증 정보를 사용하며, 전체 세션 브리지는 `ddg-agents-host`가 제공한다.
- `ddg --version`은 네트워크 접속 없이 CLI 버전을 출력한다. `ddg update status|check|apply|rollback|config`는 GitHub 릴리스의 상태·확인·적용·복원·설정을 제공한다. 기본 대상은 설정된 기본 머신과 무관하게 `local`이다. 상태·확인만 `-H all`을 허용하고, 설정은 `-H`를 받지 않는다.
- 적용·복원은 로컬 및 ID가 고정된 SSH 호스트로 제한하며, 컨테이너에는 이미지 교체만 안내한다. 비대화형 변경에는 `--yes`, 적용 시 다운그레이드에는 `--allow-downgrade`, 활성 PTY에 영향이 있는 Holder 재시작에는 별도 `--restart-sessions`가 필요하다. 커스텀 소스는 경고를 표시하고 동일한 무결성·서명 검증을 적용한다.
- 업데이트의 `--json`은 성공·실패 모두 stdout에 JSON 객체 하나를 출력하며, 진단의 비밀값은 가린다. 다른 CLI 명령에서는 업데이트 알림이나 업데이트 네트워크 요청을 발생시키지 않는다.

## 8. 첫 버전 범위와 미결정 사항

- **현재 실행 경로:** 단일 호스트 최소 터미널 서버 `ddg-terminal-server`(Holder + Core 3-Tier, libghostty-vt 1.0.1, 단일 제어권·Credit 흐름 제어)와 표준 진입점 `ddg-agents-host`(룸·탭 카탈로그 `catalog.json`, 스페이스 `cwd`·실행기 실행, 재부팅 후 목록 복원, `ext.<name>.*` 커스텀 백엔드 플러그인)가 PTY와 세션을 소유한다. 공식 GPUI 클라이언트(`native/`, `ddg-agents-native`)는 `ddg-agents-transport`(로컬 Unix 소켓 · 원격 OpenSSH · `docker exec -i` · 컨테이너 SSHD)를 통해 호스트에 접속한다. 창 닫기/`⌘+Q`/연결 단절은 detach이며 PTY는 유지되고, 탭 `×`/`⌘+W`는 `ddg-terminal-server`의 프로세스 종료·`reap` 확인 후 제거한다. 재부팅/컨테이너 재시작 뒤에는 카탈로그 목록만 `stopped_after_reboot`로 복원하고 명령을 자동 재실행하지 않는다. 최소 베이스 Docker 런타임(`docker/`)도 제공된다.
- **초기 실행 범위:** 자식 세션과 호출된 팀은 호출자와 같은 스페이스에서 실행한다. 명시적인 순차 흐름과 한도가 있는 루프부터 지원한다. 스킬 개선 및 임시 정의의 영구 등록은 사람이 검토한다.
- **미결정:** Pi 외 실행기별 고수준 어댑터 연동 방식, 터미널 메시지의 구조화 전송 형식, 상시 대기 중 프로세스 유지 여부, 툴·파일 접근 제한을 런타임에서 강제하는 방식.
- **장기 보류 (향후 검토):** GUI 3D 렌더링 지원 및 렌더링 라이브러리 선정.
